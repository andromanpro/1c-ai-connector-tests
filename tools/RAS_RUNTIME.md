# Локальный RAS для проверочного стенда

`ras_runtime.ensure_ras` подключён к проверке сеансов в `verified_yaxunit`.
Контроллеры, которые читают или восстанавливают расписание до проверки
сеансов, вызывают тот же механизм перед RAC.

Существующий конфиг стенда может явно разрешить восстановление:

```json
{
  "rac_address": "localhost:1545",
  "ras_bootstrap": {
    "agent": "localhost:1540",
    "runtime_dir": "F:/private/onec-runtime/ras-1545"
  }
}
```

Используются уже заданные `platform_bin` и `cluster`. Адрес агента не
вычисляется из регистрационного порта кластера: это разные порты.
Без `ras_bootstrap` внешний способ управления RAS сохраняется.

Перед запуском проверяются локальные адреса, разные порты RAS и агента,
наличие обоих бинарных файлов в указанной платформе, абсолютный каталог
журнала и ожидаемый UUID кластера. Готовый сервер переиспользуется только
после чтения списка кластеров через RAC. Чужой кластер, занятый
неподтверждённый порт и недоступный агент дают отказ.

Одновременный запуск защищён именованным mutex Windows; после захвата
адрес проверяется повторно. При отсутствии RAS запускается штатный
`ras.exe cluster --port=... ...` без окна, оболочки и повышения прав.
После успешной проверки процесс остаётся работающим. После перезапуска
компьютера следующий запуск проверок восстановит его тем же способом.
Установка службы Windows для этого не требуется.

Квитанция `current.json` и отдельная квитанция запуска сохраняются в
`runtime_dir` вместе с журналом. Они не содержат строки подключения и
паролей. При отказе завершается только процесс по собственному `Popen`
дескриптору; чужие процессы и сеансы 1С не закрываются.

Проверки: `py -3.14 -m unittest -v test_ras_runtime.py` из `tools`.
Подменяемые испытания проверяют отказ от удалённых адресов и другого
кластера, отсутствие агента, конкурирующий запуск, выход и таймаут
собственного процесса. Живая проба должна отдельно подтвердить создание
отсутствующего RAS и повторное использование готового.
